# Managed Knowledge Base 部署別ナレッジ（試作）

Amazon Bedrock Managed Knowledge Base をファイル置き場として使い、部署ごとに分けて検索する試作。


- ファイル置き場は Storage Browser for Amazon S3。最上位のフォルダが部署で、利用者には自分の部署のフォルダしか見えない
- Office・PDF・画像などを好きな形で置ける。置くと Markdown に書き起こし（Office は XML から、PDF・画像は生成AI）、それを KB に入れる
- 検索結果からは、書き起こす前の元ファイルを開ける
- 検索結果に他部署の文書は出ない
- タグは、フォルダ名（部署より下のすべての階層）が自動で付き、フォルダをまたぐ分類は登録済みのタグから一括で足す。検索するときは、エージェントが質問に合うタグを選んで絞り込む

リージョンは `config/app.json` の `region`（ap-northeast-1、東京）。CloudFront 用の WAF だけ us-east-1。モデルは国内の推論プロファイル（`jp.*`）を使う。

## 構成

```
画面（CloudFront + S3、React）
  │ Amplify の Authenticator で Cognito にログイン（部署 = Cognito のグループ。兼務は複数のグループ）
  ├ Storage Browser ─ 部署のフォルダ用の一時的な認証情報 ─▶ ファイル置き場のバケット（<部署>/…）
  │     （API が JWT から部署を決め、STS のセッションポリシーで部署のフォルダに絞って発行する）
  ▼
API（画面と同じ CloudFront の /api/*。WAF 付き。関数 URL は IAM 認証で CloudFront（OAC）からしか呼べない）
  ├ Storage Browser 用: 見せるフォルダの一覧・認証情報の発行
  ├ 取り込み状況の一覧、検索結果から元ファイルを開く署名付き URL
  └ チャット: Strands のエージェント ─ MCP（利用者のトークン）─▶ AgentCore Gateway
                                                              ├ ① Request Interceptor
                                                              ├ ② AgentCore Policy（Cedar）
                                                              ▼
                                                     Managed Knowledge Base
                                                              ├ ③ ACL（S3 のメタデータ）
                                                              └ ④ リソースポリシー

取り込み: ファイル置き場に置かれる ─S3 イベント▶ SQS ▶ 変換 Lambda（同時に4つまで。書き起こし・タグ選び）
          ─▶ 内部のバケットの kb-source/<部署>/…/<名前>.md と .md.metadata.json ─▶ 同期 Lambda が KB に取り込む
```

### ファイル置き場（Storage Browser）

Storage Browser は「独自の認証」で使う（`web-app/src/storage.ts`）。S3 Access Grants や Identity Pool は使わない。

- **見せるフォルダ**：API（`/api/storage/locations`）が、アクセストークンの `cognito:groups` から、属する部署の最上位のフォルダだけを返す。兼務の人には複数出る
- **認証情報**：API（`/api/storage/credentials`）が、部署に属していることを確かめてから、STS でロールを引き受けて返す（15分有効）。そのとき、そのフォルダの外には触れないセッションポリシーを付ける。ロールを引き受けられるのは API の関数だけ
- **部署は今の状態で決める**：API は、アクセストークンの `cognito:groups`（最長1時間古い）ではなく、Cognito に今のグループを問い合わせて部署を決める
- **部署から外れたら**：`acl_sync`（5分おき）が外れた人を見つけ、発行済みの認証情報を、その部署のフォルダだけ無効にする（ロールに拒否を足し、20分後に消す）
- **置いた人**：認証情報のセッション名にメールアドレスを入れるので、S3 のイベントの `principalId` から分かる。メタデータの `uploaded_by` に残す
- **上書き・移動・名前の変更**：文書 ID は元ファイルのキーから作る。上書きは書き起こし直し、移動・名前の変更（コピーと削除）は古い書き起こしを消して新しく作る
- 利用者が触るファイル置き場のバケットと、書き起こしなど内部のバケットは分けてある。利用者の認証情報では内部のバケットを読めない

Storage Browser の表示は英語のまま（日本語の文言は同梱されていない。`displayText` で差し替えられる）。

### 台帳（元ファイルと書き起こしの紐付け）

元ファイル・書き起こし・タグ・状態の紐付けは、DynamoDB の台帳が正本（`functions/shared/ledger.py`）。S3 には書き起こしの本文と KB 用のメタデータを置き、メタデータは台帳から作る。

| 表 | キー | 持つもの |
|---|---|---|
| 文書（`Documents`） | 部署 ＋ 元ファイルのキー | 書き起こしの場所、中身の SHA-256、元ファイルの版、状態と理由、フォルダ名のタグ・追加のタグ、置いた人、マルウェア検査の結果、S3 のイベントの前後（sequencer）。索引は中身（`bySha`）と状態（`byStatus`） |
| 中身（`Contents`） | 中身の SHA-256 | 書き起こしの控えの場所、追加のタグ、最後に使った日時 |
| タグ（`Tags`） | 部署 ＋ タグの名前 | 説明、色、並び順、アーカイブ、版（同時に直したときに後の保存を断る）、作った人・直した人と日時。部署ごとに `#seeded` の行（最初の一覧を入れたしるし） |

- **順番の入れ替わり**：SQS は順番を保証しない。S3 のイベントは sequencer、マルウェア検査の結果は元ファイルの版で比べ、台帳より古いものは捨てる（条件付き書き込み）。書き起こしの途中で新しい版が置かれたら、古い結果は捨てる
- **保護**：元ファイルと書き起こしのバケットは版を持ち（古い版は90日で消す）、スタックを消しても残す。台帳の表はポイントインタイムリカバリ（35日）・削除保護・スタックを消しても残す。`cdk destroy` のあとも、これらは手で消すまで残る
- **毎日の突き合わせ**（3:00、`scripts/reconcile.py` でも動く）：台帳に無い元ファイルを登録（台帳を入れる前の文書の移行もこれ）、元ファイルの無い台帳を消す、消えた書き起こしを控えから作り直す、台帳に無い書き起こしを消す、止まったものを入れ直す（2回で諦めて失敗にする）、使われない控えを30日で消す

### 部署の分離（4層）

スライド「[Agentic RAG の Fine-grained access control](https://speakerdeck.com/ren8k/agentic-rag-fine-grained-access-control)」の強化構成に従う。

| 層 | 仕組み | 何を防ぐか | 実装 |
|---|---|---|---|
| ① ツール層 | Interceptor が JWT を検証し、Retrieve の `userContext` に JWT の email を入れる。エージェントが入れた値は上書きする | エージェント（モデル）による他人へのなりすまし（プロンプトインジェクション・ハルシネーション） | `functions/interceptor` |
| ② ツール層 | Cedar のポリシーで、`userContext.userId` が JWT の email と一致する Retrieve だけを許す。それ以外（AgenticRetrieveStream を含む）は既定で拒否する | Interceptor の不具合・設定漏れ | `cdk/lib/prototype-stack.ts` の `RetrieveOwnIdentityOnly` |
| ③ リソース層 | 文書ごとのメタデータに ACL（部署の人のメールアドレス）を書く。KB は `userContext` の人が許された文書だけを返す | 他部署の文書が検索結果に混ざること | `functions/convert`・`functions/acl_sync` |
| ④ リソース層 | KB のリソースポリシーで、Gateway の実行ロール以外からの `bedrock:Retrieve` を拒否する | Gateway を通らない直接の検索（SDK・CLI・別の Gateway） | `KbPolicy` |

加えて、API は元ファイルを渡す前に、利用者の部署をもう一度確かめる。

**ACL は人単位で書く。** Managed KB の S3 の ACL は、`Type` に `USER`（メールアドレス）しか書けない。そのため部署の人が変わったら、その部署の文書の ACL を書き直して同期する（`scripts/users.py` が `acl_sync` を呼ぶ）。確かめたところ、書き直しから約100秒で検索結果に反映された。

### 書き起こし

Managed KB のパーサーは `SMART_PARSING` 固定で、ほかのパーサーを選べない。検証したところ、PDF・Word・PowerPoint・CSV・Excel は取り込みのあと時間をおいてもう一度解析され、その結果で先の結果が置き換わる。TXT・MD・HTML は1回だけ。日本語の PDF・Word では、この2回目で本文が崩れることを確認した（原文に無い文字列への置き換え、条文の欠落など）。この挙動は設定で変えられないので、KB には自前で書き起こした Markdown だけを渡す。

| 形式 | 書き起こし方 |
|---|---|
| docx・pptx・xlsx | **XML から読む**（`functions/convert/office.py`）。本文・表・テキストボックス・ヘッダー・コメント・グラフの実データ・SmartArt・図形のつながり（コネクタ）・グループ内の図形を取る。生成AIは通さないので、書き写し間違いや出力の途中切れが無い |
| Office の中の画像 | XML に中身が無いので、画像だけを Claude に説明させ、元の位置に差し込む（並列6本）。同じ画像は1回だけ。EMF・WMF は読めないと書く |
| PDF | ページを画像にして Claude に読ませる（8ページずつ並列）。出力が上限で切れたまとまりは1ページずつ読み直す。300ページまで |
| 画像 | Claude に説明させる |
| doc・xls・html | XML で読めない古い形式は Converse API に渡す（文字だけ） |
| ppt | 読めない。pptx で保存し直してもらう |
| txt・md・csv | そのまま |

python-docx は、本文の段落しか返さない（表・テキストボックス・ヘッダー・画像を拾わない）ことを確かめたので、XML を直接たどっている。

Excel は表をそのまま Markdown の表にする。大きな表は、見出し行を繰り返しながら50行ずつに区切る（検索で見出しが分かるように）。キャッシュ値の無い数式は数式のまま、グラフの値はキャッシュ、無ければ参照先のセルから取る。

Office の読み取りは `scripts/make_office_fixtures.py` が作る試験用の書類で確かめる（`scripts/check_office.py` は手元で、`scripts/verify.py` はデプロイ後に生成AIまで含めて）。

### タグ

生成AIには選ばせない。タグは次の2つを合わせたもの（メタデータの `tags`。`listContains` で絞り込む）。

| 種類 | 付け方 | 変え方 |
|---|---|---|
| フォルダ名のタグ（`folder_tags`） | 部署のフォルダより下のすべての階層（`sales/契約/2026/見積.pdf` → 契約・2026） | フォルダを移す |
| 追加のタグ（`extra_tags`） | 取り込み状況の一覧で、絞り込んで選んだファイルに一括で足す・外す。選べるのは部署の追加タグの一覧（管理者が画面で変える。アーカイブしたものは除く）だけ | 同じ画面で一括で外す |

追加のタグは中身（SHA-256）に紐づけて持つので、フォルダを移しても（コピーと削除でも）引き継がれる。書き起こしも中身ごとに控えておき、同じ中身なら使い回す（移動・名前の変更・コピーで生成AIを呼ばない）。控えは文書を消しても残す（移動では、消す方が先に処理されることがあるため）。

タグの付け方を変えたときは `scripts/retag.py` で既存の文書を付け直す（書き起こしはやり直さない）。

**追加タグの一覧**は DynamoDB の `Tags` 表に部署ごとに持ち、管理者が「タグの管理」の画面で変える（1タグ1行）。

- 説明と色を付けられる。説明は取り込み状況でタグにマウスを乗せたときに出し、エージェントのタグの一覧にも入れる（どのタグで絞るかを選ぶ手がかり）
- 付いている件数を台帳から数えて出す
- **アーカイブ**: 一括で足す候補に出さないが、付いている分は残り検索にも使われる。戻せる
- **消す**: 付いている文書があれば、文書から外して消す（台帳・KB のメタデータ・書き起こしの先頭のタグの行も直し、入れ直す）か、消さずにアーカイブするかを選ぶ
- 使えるタグ（アーカイブを除く）は部署ごとに30個まで。名前は20文字まで、`/` を含まず `#` で始まらないもの。名前は変えられない（付いている文書の付け替えになるため）
- 最初の一覧は、部署の一覧を初めて読んだときに入れる（`config/app.json` の `tags` に、すでに文書に付いているタグを足したもの）
- 一覧に無いのに文書に付いているタグがあれば、画面に警告を出す

### メタデータ

```json
{
  "metadataAttributes": {
    "department": "sales", "tags": ["契約", "2026", "要確認"],
    "folder_tags": ["契約", "2026"], "extra_tags": ["要確認"],
    "original_key": "sales/契約/2026/見積書.pdf", "file_name": "見積書.pdf", "folder": "契約/2026",
    "uploaded_by": "…", "malware_scan": "NO_THREATS_FOUND", "content_sha256": "…"
  },
  "accessControlList": [{ "Name": "…@example.com", "Type": "USER", "Access": "ALLOW" }]
}
```

タグでの絞り込みは `listContains`・`orAll`・`in` が Managed KB で効くことを確かめた。

**エージェントがタグを知る方法。** 質問のたびに、利用者が見られる部署の「取り込み済み」の文書を台帳から数え、フォルダの階層（`契約/2026（12件）`、件数の多い順に80まで）と追加のタグ（件数つき）を指示文に入れる（5分控える）。部署の追加タグの一覧ではなく実際に付いているものなので、0件のタグで絞って何も返らないことが無い。Gateway の `filter` の説明は固定の文にし、タグの一覧は持たせない（一覧を増やすたびにデプロイしないため）。

絞り込むのは、利用者がフォルダ・タグ・分類を指して聞いたときだけ。文書番号などにタグと同じ文字が含まれるだけでは絞らない（「Q-2026-0901」で「2026年度」に絞る行き過ぎが評価で見つかったため）。絞って0件なら絞らずに探し直す。使った検索（道具・問い・絞り込み）は質問の結果と操作の記録（`chat`）に残す。

**空の値は入れない。** 空のリスト（タグが1つも付かなかったときの `"tags": []`）の属性があると、Managed KB はその文書を取り込まない（取り込みは「一部の文書をクロールできなかった」で終わり、文書の一覧にも出てこない）。空の値は項目ごと除く（`without_empty`）。評価セットで2つの文書に1問も届かないことから見つけた。

## 使い方

```sh
uv sync                                             # スクリプトの依存（pyproject.toml → .venv）
./scripts/build_functions.sh                        # Lambda の配布物（Docker 不要）
(cd web-app && npm ci && npm run build)             # 画面
(cd cdk && npm ci && npx cdk deploy --all --outputs-file ../.state-outputs.json)   # WAF（us-east-1）も

uv run python scripts/users.py test-accounts        # 確認用の3人
uv run python scripts/users.py create <email> sales legal
uv run python scripts/users.py leave <email> legal
```

パスワードは `~/managed-kb-test-accounts.txt`（600。`MKB_ACCOUNTS_FILE` で変えられる）に書く。画面の URL は `.state-outputs.json` の `WebUrl`。スクリプトが共通で使う設定は `scripts/project.py`。

部署とタグは `config/app.json` で変える。部署を足したら、デプロイして（Cognito のグループが増える）人を入れる。

## 確かめ方

```sh
./scripts/verify_all.sh                         # すべて順に（1〜2時間。結果は final_*.log）
.venv/bin/python scripts/verify.py              # 書類を置くところから
.venv/bin/python scripts/verify.py --skip-upload
.venv/bin/python scripts/verify_membership.py   # 部署の入れ替えと止まった変換（verify.py のあと）
.venv/bin/python scripts/verify_burst.py        # まとめて置いたときの順番待ち
```

確認用の書類は `testdata/`（[testdata/README.md](testdata/README.md)）。`testdata/office` は `scripts/make_office_fixtures.py` が作る。書類は Storage Browser と同じ手順（API から部署のフォルダ用の認証情報をもらって S3 に置く）で置く。

ファイル置き場では、他部署のフォルダの認証情報が出ないこと、自部署の認証情報でも他部署のフォルダ・バケット全体・内部のバケットに触れないこと、置いた人が残ること、名前の変更で古い書き起こしが消えることを確かめる。部署の分離は4層それぞれを個別に確かめる。

- ①：営業の人が法務の人を名乗っても、営業部の文書しか出ない
- ②：Interceptor に一時的に故障（別人を入れる）を起こすと、Cedar が拒否する。確認のあと故障は必ず戻す
- ③：部署ごと・兼務の検索結果
- ④：管理者の認証情報でも、直接 Retrieve すると `AccessDeniedException` になる

2026-09-27（引き継ぎのための整理のあと）の時点で、`verify.py` 46/46、`verify_tags.py` 18/18、`verify_tag_admin.py` 29/29、`verify_membership.py` 10/10、`verify_malware.py` 13/13、`verify_burst.py` 2/2、`verify_ledger.py` 17/17、`verify_ops.py` 24/24、`verify_large_pdf.py` 5/5、`eval_rag.py` 正答 21/21・控え 4/4。画面は Playwright で、Storage Browser、途中経過の表示、タグの一括指定、書き起こしの画面を確かめた（ヘッドレスのブラウザは PDF を表示しないので、元ファイルの並べ表示は PDF として返ることだけを確かめた）。

## 運用の仕組み

- **部署の入れ替え**：`acl_sync` が5分おきに部署の人を前回と比べ、変わった部署だけ ACL を書き直して同期する。Cognito のコンソールで変えても拾う（最長5分＋同期の約100秒）。`scripts/users.py` は変えた直後に呼ぶので、すぐ反映される。即時にしたいなら、CloudTrail の証跡を作り、Cognito のグループの変更を EventBridge で拾う（証跡が無いと EventBridge に届かない）
- **保護（暗号化）されたファイル**：Purview（MIP）やパスワードで保護された Office・PDF と、`.pfile`・`.ppdf` などは、中身を読まずに見分けて「対象外（保護）」にし、置いた人に知らせる（「失敗」にしない）。この仕組みには「公開」のラベルの文書だけを置く運用を前提に、復号はしない。確認用のファイルは `testdata/protected/`（手元で msoffcrypto-tool・pikepdf で暗号化したもの）
- **マルウェアの検査**：ファイル置き場は GuardDuty のマルウェア検査（S3 向け）で検査する。書き起こしは検査が終わってから（EventBridge の検査結果 → SQS）。脅威が見つかったものは取り込まず「ブロック」と出し、バケットポリシーで誰も読めなくする。そのファイルのタグは GuardDuty 以外は書き換えも削除もできない（書き換えられると読めるようにできてしまう）。置ける形式は制限しない（ファイル置き場なので）。書き起こせない形式・大きすぎるものは「対象外」と出す
- **変換の順番待ち**：変換は SQS に並べ、同時に4つまで（まとめて置かれても Bedrock の上限にかからないように）。順番の入れ替わりは台帳で扱う（上の「台帳」）
- **止まった変換**：変換 Lambda が落ちると（時間切れ・メモリ不足）、SQS がもう1回やり直す。2回続けて止まったものは DLQ に移り、`ConvertFailed` が台帳で失敗にする。それでも60分たって終わらないものは「止まっている可能性」と出し、毎日の突き合わせが入れ直す
- **大きな PDF**：120ページを超える PDF は Step Functions で24ページずつに分け、同時に3つまで書き起こして最後につなぐ（2,000ページまで）
- **書き起こし直し**：`scripts/reconvert.py` が、ファイル置き場のファイルを変換の列に入れ直す（モデル・プロンプト・読み方を変えたとき）。マルウェアの検査はやり直さない。人が直したタグは残る
- **タグ**：フォルダ名のタグ＋追加のタグ（上の「タグ」）。追加タグの一覧は部署ごとに DynamoDB に持ち、管理者（Cognito の `admins` グループ）が画面で説明・色・並び順・アーカイブ・削除を変える
- **チャット**：質問を受け付けたらすぐ処理の ID を返し、答えは裏で作って DynamoDB に書き足す。画面は1秒弱ごとに問い合わせ、書けた分から出す。1回の呼び出しが短いので、CloudFront の60秒の上限にもかからない
- **エージェント**：1つの事実は Retrieve、込み入った質問は AgenticRetrieveStream を使う。どちらも Interceptor・Cedar・ACL の守りは同じ。兼務の人は検索する部署を選べる（Interceptor が検索の条件に部署を足す。部署を選んだときはエージェント型の検索は使わない）
- **ページ**：書き起こしの `<!-- page N -->`・`## スライド N` から、回答の根拠がどのページかを割り出し、元ファイルのリンクに出す（PDF はそのページを開く）。Managed KB のページ番号は取り込みの後に消える不具合があるので使わない
- **API の入口**：CloudFront の `/api/*` に WAF（AWS の共通ルール・既知の悪い入力・IP ごとに5分で1000回まで）。利用者のトークンは `x-app-token` ヘッダーで送る（Authorization は OAC の署名が使う）。本文があるときは `x-amz-content-sha256` を添える
- **画面**：Storage Browser は日本語の文言に差し替え、パンくずリストはバケット名を出さず部署名で出す。取り込み状況は Storage Browser で開いているフォルダに合わせて絞る

## 監視・記録・お知らせ・書き起こしの修正

- **監視**：アラームはすべて SNS のトピック（`AlertsTopic`）に流す。宛先は `config/app.json` の `alertEmail`（空なら送らない。あとから SNS で購読を足してもよい）。ダッシュボードは `mkbproto-overview`

  | アラーム | 条件 |
  |---|---|
  | 変換の DLQ | 2回続けて止まった変換がある |
  | 変換の列の待ち | 30分以上つかえている |
  | Lambda のエラー | 変換・API・Interceptor・ACL・突き合わせ・同期・大きな PDF・失敗先 |
  | 大きな PDF | Step Functions が失敗した |
  | 取り込みの失敗 | KB が取り込まなかった文書がある（同期の Lambda が数える。KB は黙って飛ばすため） |
  | API の 500 | 例外を 500 にしているので、Lambda のエラーとは別にログから数える |
  | Bedrock の上限 | 5分に5回以上、呼び出し上限にかかった |
  | 突き合わせ | 入れ直しても終わらないものがある、ずれを10件以上直した |

- **操作の記録**：
  - アプリの操作（元ファイルを開く・質問と答えに使った元ファイル・タグの変更・書き起こしの修正・認証情報の発行・権限の無い操作の試み）は、API が `/mkbproto/audit`（13か月）に書く
  - ファイル置き場への直接の操作（Storage Browser）と、管理の書き込み操作は CloudTrail（`mkbproto-audit`）に残る。認証情報のセッション名がメールアドレスなので、誰の操作か分かる。記録は1年間は書き換えも削除もできないバケット（Object Lock のガバナンスモード）に置き、改ざんの検知も有効。CloudWatch Logs にも送る（13か月）
  - `scripts/audit.py --user <email>` で両方を時系列に並べて見られる
  - 証跡があるので、Cognito の部署の変更を EventBridge で受け、ACL をすぐ書き直す（5分おきの突き合わせは取りこぼしの備えとして残す）
- **お知らせ**：書き起こしの失敗・対象外・ブロックを、置いた人の画面の「お知らせ」に入れる（90日）。`config/app.json` の `notifyFrom` に SES の送り元を設定すると、メールも送る（SES のサンドボックスでは検証済みの宛先にだけ届く）
- **書き起こしの修正**：取り込み状況の一覧・チャットの元ファイルから、書き起こしをページ（PDF）・スライド・シートごとに見て、元ファイルのそのページと並べて直せる。直した書き起こしは中身ごとに持ち、同じ中身の文書すべてに効く。書き起こし直し（`reconvert.py`）でも残り、`--discard-edits` を付けたときだけ捨てる。最初に直す前の生成AIの書き起こしは `control/transcripts/<sha>.orig.md` に残る。ほかの人が先に直していたら保存を断る

## 試作としての割り切り・残っていること

- **部署の人数が多いと ACL が大きくなる。** 1文書に部署全員のメールアドレスを書くため。人数の上限は未確認
- **フォルダ名の揺れがそのままタグになる**（「契約」と「契約書」など）。フォルダを作れる人を絞るか、決まりを設ける
- **1つの文書は1つのフォルダにしか置けない。** フォルダをまたぐ分類は追加のタグで表す
- **話題がフォルダ名と合うと、エージェントはそのフォルダで絞る**（「就業規則」→ `規程/人事`）。同じ文書を別のフォルダにも置いていると、絞った側の分だけが検索される。試作ではこれで良いとした（2026-09-27）
- **Storage Browser の最初の一覧（トップ）には、バケット名の列が残る。** 表示文言では消せない（部品の差し替えが要る）
- **AgenticRetrieveStream は部署を選んだ検索に使えない。** 検索する KB が管理者の設定で決まっていて、部署の条件を足す口が無いため
- **チャットの途中経過のため、利用者のアクセストークンを Lambda の非同期呼び出しに載せている。** トークンは最長1時間有効
- **ACL は「認可」ではない**（AWS の注意書き）。上流で認証したうえで userContext を入れる前提で、①②④と組み合わせている
